# Spike Report: BURL-D001 Span Invalidation Under Source Splicing

> **Status: complete.** Executed 2026-08-05. Every number below was measured on the machine and toolchain recorded in section 3; nothing here is an estimate.

## 1. Context & Objective
- **Triggering upstream file/section:** `.constitution/architecture/risks.md` risk 7 (Span Invalidation Under Splicing); `.constitution/tech-spec/adrs/ADR-007-span-preserving-splice-edits.md` decision 1 and its first Negative consequence; `ADR-008-save-and-commit-granularity.md`'s final unsettled Negative on timer/FFI-thread synchronization.
- **Target:** How the Core Engine maintains source spans across a splice, the Note size at which the chosen strategy stops meeting the 16ms frame budget in `prd/constraints.md`, and the shape by which the tier 2 idle-write timer synchronizes with the synchronous `update_block`/`commit_block` FFI calls it races.

The risk is a silent data-corruption mode rather than a crash: splicing one Block shifts every subsequent byte offset, so a stale span map writes a later edit into the wrong region of the file. ADR-007 names whole-file reparse as the mitigation because it makes an incorrect span map unrepresentable, but the cost of that choice had never been measured. ADR-008 additionally left the timer's locking discipline open, having only observed that reusing `db::connection`'s process-wide mutex naively would put a keystroke behind a lock held across a disk write.

## 2. Codebase Baseline
- **Current state of the parser.** `rust/src/markdown/parser.rs` drives `Parser::new_ext(input, options)` with `ENABLE_STRIKETHROUGH | ENABLE_TASKLISTS` and folds the event stream into `Vec<AstNode>`. It carries no span information of any kind, and `rust/src/markdown/ast.rs` has no byte-range field on any variant — consistent with ADR-007 decision 3, which forbids one. There is no serializer anywhere in `rust/src/`, so nothing on the save path can rewrite an unedited region today for the simple reason that nothing on the save path writes at all.
- **`Parser::into_offset_iter()` is present and yields a source range for every event, inline events included**, so ADR-007 decision 8's map is available from the same pass that builds the AST. `ENABLE_YAML_STYLE_METADATA_BLOCKS` plus `Tag::MetadataBlock` locates the frontmatter as a span like any other, so ADR-007 decision 5 costs no separate code path.
- **Resolving a rendered offset to a source offset is *not* a matter of interpolating inside a run, and this Spike originally claimed otherwise.** ADR-007 decision 8 and `BURL-D003`'s Gherkin both use `hello **bold** world` as the worked example, where rendered offset 6 does resolve to source offset 8. That example is the case where every run's rendered length equals its source length, and interpolating `source.start + (offset - rendered.start)` happens to be right. It is wrong wherever those lengths differ, which is not an exotic corner. Measured against `pulldown-cmark` 0.12.2 with the same map builder:

  | Source | Run | Rendered len | Source len | Consequence of interpolation |
  | :--- | :--- | ---: | ---: | :--- |
  | ``a `code span` b`` | `` `code span` `` | 9 | 11 | Rendered offset 2 is the `c` of `code`; interpolation returns source 2, which is the **backtick**. Every offset in the run is short by the opening delimiter, and by the end of the run the error has grown to the width of both. |
  | `x &amp; y` | `&amp;` | 1 | 5 | The run collapses five source bytes to one rendered byte; nothing inside it can be addressed by interpolation at all. |
  | `caf&eacute; au lait` | `&eacute;` | 2 | 8 | Rendered offset 4 (the second byte of `é`) interpolates to source 4, which is the `e` inside `&eacute;` — an interior byte of an entity reference, and in the general case not necessarily a char boundary. |
  | `num &#65; ref` | `&#65;` | 1 | 5 | As above, for numeric references. |

  Two further shapes matter to D003 even though interpolation survives them. A backslash-escaped run (`esc \*not emphasis\* end`) has matching lengths but a source range that *excludes* the backslash, and inline-link runs cover only the link text (`[link](url) tail` yields runs at source `1..5` and `33..38`), so **run source ranges do not tile the Block's source**. Anything that reconstructs a selection by concatenating run sources, or that assumes rendered length summed over runs equals the Block's rendered text, is wrong for the same underlying reason.

  **The constraint this hands `BURL-D003`:** interpolation within a run is sound only where that run's rendered length equals its source length, and the map must therefore record enough to tell the two cases apart — carry the run's kind, or simply its rendered and source lengths, and treat any run where they differ as atomic. For an atomic run, a rendered offset resolves to the run's whole source range clamped to its endpoints, never to an interior byte. This is what D003's last Gherkin — "the extracted text is exactly the source spanned by the selection, delimiters included" — actually requires: for `` a `code span` b`` the delimiters are *inside* the run's source range, and only a run-atomic resolution returns them. Code spans, entity references and escaped runs each need explicit handling; a `hello **bold** world` fixture will not detect their absence.
- **Block span endpoints are safe to splice on.** All 1453 block spans produced over a 128 KiB adversarial corpus — 2906 endpoints — are valid UTF-8 char boundaries with `start <= end <= len`. This matters because `String::replace_range` panics rather than erring on a non-boundary index, and a panic across the FFI boundary is not a recoverable `AppError`. The check covers block spans only; it says nothing about the inline map, whose hazard is the one above.
- **The round-trip property already holds against the real parser.** Splicing each Block's own unmodified source back over its span reproduced the file byte-for-byte across 287 blocks (32 KiB prose), 2135 blocks (256 KiB prose) and 2861 blocks (256 KiB adversarial). This is the executable form of the Edit Fidelity constraint that `tech-spec/guidelines.md` makes mandatory for `BURL-D003`, and it passes on the prototype, so it is a gate D003 can adopt rather than a risk it must discover. It is a **block-span** property: it exercises neither rendered-to-source resolution nor the inline map, so it is not evidence for either.
- **Existing concurrency precedent.** `rust/src/db/connection.rs` holds one process-wide `OnceLock<Mutex<Connection>>` and exposes `with_connection`, which acquires the mutex and runs a closure against `&Connection`. The lock is released when the closure returns, so the construct is sound in itself; the hazard ADR-008 identified is entirely about *what a caller puts inside the closure* and about whether any *other* lock is layered over the same critical section.
- **Discovered constraint, not previously recorded anywhere.** The per-keystroke cost of ADR-008 tier 1 is not small. Writing the full working source into the encrypted `drafts` row costs 7.96ms (median, 102 KiB) and 22.79ms (median, 1 MiB) with SQLite's default `journal_mode = DELETE` and `synchronous = FULL`. That is half the 16ms budget at 102 KiB and past it outright at 1 MiB, and it is roughly a thousand times the cost of the buffer substitution and span arithmetic it accompanies. ADR-008 tier 1 calls itself "cheap"; measured against the encrypted index on a real filesystem, it is the single most expensive thing on the typing path. See section 6.3.

**Two methodological points that changed the answers, recorded because a re-run that skips them will not reproduce these numbers.**

First, `/tmp` on this machine is `tmpfs`. Every file and database measurement taken there runs at memory speed with `fsync` as a no-op, and the first pass of this Spike understated tier 2's atomic write by roughly 20x. All I/O figures below were re-taken against ext4 on NVMe.

Second, a SQLCipher row write costs radically different amounts depending on whether the *content* changes. Rewriting an identical 102 KiB value costs 0.22ms; writing a value that differs by one byte costs 7.96ms — a factor of 36. A tier 1 benchmark that loops over a constant string therefore measures nothing of interest, which is exactly the trap the first pass fell into. Every tier 1 figure below mutates the buffer on each call, as a keystroke does.

Timings are taken with `std::time::Instant` around each iteration, five warmup iterations discarded, samples sorted, median and p95 reported by index. Parse measurements run tight (400 iterations, or 60 above 1 MiB, capped at 3s per cell). Persistence and contention measurements are *paced* — an 8ms idle gap between calls — because after an idle gap the core is at a lower clock and the working set is out of cache, which is the state a real keystroke arrives in; the tight-loop figure for the same call is optimistic by 3-40x and is not the number an implementer should plan against.

**Run-to-run variance is larger than a single pass suggests, and section 4 reports the conservative end of it.** Three full passes were taken. In the mid ladder — 20 KiB to 1 MiB, which is where the decisions live — medians agreed within roughly 15%. Outside it they did not. The 5 KiB cell moved 0.061 / 0.063 / 0.253ms across passes, because the first two passes selected a container Block as the splice target and editing it changed the document's structure into a cheaper event stream; only the third pass, which selects a *leaf* Block, is measuring the intended operation, and the earlier two are discarded rather than averaged. The dense-inline 1 MiB p95 moved 76.8 / 163.1 / 77.7ms, a single-pass outlier from scheduler interference at a cell with only ~40 samples. Neither a "±15%" claim nor any single pass should be quoted as the tolerance; where a number below drives a decision, section 4.2 gives the spread and the decision uses the least favourable value.

The `prose` corpus carries frontmatter with unmanaged keys, headings, paragraphs at a realistic emphasis/inline-code/link/wikilink density, bullet and task lists with one level of nesting, fenced code and blockquotes. **The 52.4 KiB row is internally impossible and must not be quoted.** It reports `parse-only` at 2.520ms and `splice+reparse` at 1.736ms, but `splice+reparse` strictly contains more work than `parse-only` does, so no ordering of real costs produces that. It is a cold-cell artifact: it is the first cell after the two sub-millisecond small rows, and its `parse-only` measurement absorbs the clock ramp that the following cells do not pay. Its neighbours at 20.9 KiB and 101.7 KiB bracket the true value, and the linear fit through them puts a 52 KiB reparse near 1.8ms, which is what the `splice+reparse` column reports. The row is left in the table rather than deleted because deleting an inconvenient measurement is worse than labelling it.

Three things the table says, with that row set aside. The substitution itself is free relative to the parse — `splice+reparse` tracks `parse+spans` within noise, so the cost of a committed splice *is* the cost of the reparse. Building the span map is not a fixed constant factor: the ratio of `parse+spans` to `parse-only` rises monotonically with Note size, from 1.11x at 2.5 KiB through 1.15x at 102 KiB and 1.26x at 1 MiB to 1.35x at 4 MiB (the 52.4 KiB cell's apparent 0.85x is the artifact above). It grows because the map's per-run allocations scale with inline-run count while `pulldown-cmark`'s own scan does not; it is still far below the 2x a second pass would cost, which is the point that matters. And the curve is very close to linear in bytes across four orders of magnitude, so extrapolation between measured points is sound.

The adversarial p95 spread (156-227 KiB) is wide because that cell sits on a steep part of the curve between two widely-spaced measurements, so a small perturbation in either endpoint moves the interpolated crossing a long way. The right reading is not that the true value is 156 KiB but that the crossing for dense inline content is **somewhere between roughly 150 and 230 KiB**, and 150 is the number to plan against.

The pair to plan against is therefore: **a committed splice stays inside one 60fps frame up to roughly 360 KiB of ordinary Markdown, and roughly 150 KiB of the densest Markdown a person could plausibly write.** For scale, the 101.7 KiB prose corpus is about 15,000 words across 859 Blocks — already an unusually long single Note for a personal knowledge bundle — and it reparses in 3.4ms, a 4.7x margin. At 257 KiB the margin is still 1.5x. The adversarial 103 KiB corpus reparses in 6.9ms, a 2.3x margin, and that corpus is denser than real prose by construction.

### 4.4 Timer / FFI-thread contention

A keystroke thread (standing in for the Dart caller running `#[frb(sync)]` `update_block`) mutates the working source and span map and writes the tier 1 draft row, paced at 8ms. A Core-owned timer thread fires the tier 2 write concurrently. The timer period is **40ms rather than ADR-008's ~1s**, deliberately: that is a 25x exaggeration of the collision rate, chosen so the tail is bounded by measurement rather than by argument. Four lock shapes, at `WAL` + `NORMAL`. **This table is a single pass (n=1 per cell, 250 keystrokes each) and was taken only in the WAL configuration**; the paragraph after it gives the one non-WAL comparison, also single-pass. The lock-shape conclusion rests on a gap of two to three orders of magnitude in the two bolded columns, which no plausible single-pass variance closes, but the individual figures should not be quoted as though they were replicated.

The same run with SQLite defaults (`DELETE` journal, `synchronous = FULL`) at 1024.6 KiB, which is the configuration the code would have shipped with had nobody measured: naive single mutex gives a keystroke median of **63.709ms** and p95 of **90.436ms**, with the buffer mutation alone — work that takes 60 microseconds — waiting a median of 26.530ms and a p95 of **55.947ms** for the lock, while tier 2 held it for a median of 51.597ms. That is ADR-008's warning reproduced as a number.

The decisive column is the mutation one, because it isolates lock wait from work. Under the naive shape a keystroke waits up to 10.4ms (p95, WAL) or 55.9ms (p95, defaults) in front of an operation with no I/O in it at all. Under the chosen shape it never waits: 0.031ms and 0.336ms p95, indistinguishable from the uncontended baseline, and the tier 2 side never holds the state lock for longer than a single microsecond even at 1 MiB.

The `Arc` copy-on-write is what buys the last column. A deep-copy snapshot still holds the state lock proportionally to Note size (7.6ms median at 1 MiB); an `Arc::clone` is a refcount bump, and the copy is paid instead by whichever *single* subsequent keystroke first calls `Arc::make_mut` while the timer's snapshot is still alive — visible as the mutation median rising from 0.062ms to 0.136ms at 1 MiB, which is 0.8% of the frame budget.

## 5. Options & Trade-offs
- **Option A — whole-file reparse after every committed splice.** Correct by construction; an incorrect span map cannot be represented. Cost is O(file) per committed edit, measured at 3.4ms for a 102 KiB Note and 9.6ms at 257 KiB, crossing the frame budget at p95 around 360 KiB of prose. ADR-008's tiering is what keeps this off the per-keystroke path.
- **Option B — arithmetic offset adjustment on the committed path.** Roughly 700x cheaper (0.005ms against 3.4ms at 102 KiB). Rejected, and on two independent grounds rather than one. The measured ground: reparse already fits the budget with a 4.7x margin at a Note size that is itself far beyond typical, so there is nothing to buy. The structural ground is the stronger one and would hold even if the timings had come out badly — a *committed* splice is exactly the operation that may change a Block's node shape (ADR-007's second Negative: a paragraph gaining a leading `- ` becomes a list), so arithmetic would produce correctly-shifted offsets into a tree that no longer describes the file. The errors that produces are silent, which is the whole of risk 7.
- **Option C — reparse, with an offset-arithmetic fallback above a size threshold.** Rejected as the worst of both. It puts the silent-corruption path into the codebase and arranges for it to be exercised only on the rarest inputs, where it gets the least testing. If reparse ever stops fitting, the answer is an incremental parse over a bounded region with a Stage 3 pass behind it, not a fallback that trades correctness for latency at exactly the moment nobody is watching.
- **Timer synchronization, option 1 — one process-wide mutex over working source, span map, connection and file write.** Rejected on measurement: section 4.4, keystroke p95 of 90.4ms under default SQLite settings, with a lock-wait p95 of 55.9ms in front of work that does no I/O.
- **Timer synchronization, option 2 — separate locks, timer deep-copies the buffer under the state lock.** Rejected: correct, but the state lock is still held for a time proportional to Note size (7.6ms median at 1 MiB), and the copy is paid by the wrong party, on a thread that has all the time in the world, while blocking one that does not.
- **Timer synchronization, option 3 — separate locks, `Arc` copy-on-write snapshot, state lock released before either side performs I/O, plus a dedicated tier 2 write lock no keystroke can contend for.** Chosen; see 6.2.

## 6. Execution Directives

### 6.1 Span maintenance: Option A, unchanged, and this settles it
- **Chosen option:** `BURL-D003` reparses the whole working source and rebuilds the span map after every committed splice, exactly as ADR-007 decision 1 and `risks.md` risk 7 specify. Nothing about the specification changes; what changes is that it is now measured rather than assumed. This decision concerns the *block* span map and is unaffected by the inline-resolution defect in section 2, which is a correctness constraint on how the map is consulted rather than on how often it is rebuilt.
- **Why it fits:** at the Note sizes this product is for, reparse costs 0.1-3.4ms against a 16ms budget, and the substitution is free relative to it. The optimization risk 7 held in reserve is not needed, and buying it would cost the one property the design exists to guarantee.
- **When offset arithmetic *is* warranted, stated exhaustively so it is not rediscovered as a good idea:** only in the `update_block` buffering case that ADR-008 decision 2 already settles — one Block's text changed, its structure deliberately not re-derived until blur, a single uniform delta applied to later spans, and a full reparse following immediately at `commit_block`. The measurements confirm that case is not merely permissible but necessary: reparsing on every keystroke would cost 3.4ms per character at 102 KiB (21% of the frame budget, on top of tier 1's own 2.4-8.0ms) and 19.7ms at 512 KiB, which is over budget on its own. Outside that case — that is, on every path listed in ADR-007's first Negative — arithmetic is forbidden.
- **The measured ceiling, recorded rather than guarded against.** Above roughly 360 KiB (prose) or 150 KiB (dense inline) — the least favourable of three passes, per section 4.2 — a blur exceeds one frame. `BURL-D003` must **not** add a size threshold, a fallback strategy, or a background-thread escape hatch for this; the failure mode above the ceiling is a visible dropped frame on a discrete, infrequent action, which is a far better thing to have than a second code path. The ceiling belongs in a doc comment on the reparse entry point so the next person to look at a slow blur finds the number instead of re-deriving it.
- **Three obligations the measurements hand D003 directly.** Build the span map in the same pass as the AST — the incremental cost is 1.11-1.35x rising with size, whereas a second pass would be 2x. Keep the round-trip property test as the primary gate: it passed on the prototype across 5283 blocks in three corpora, so it is a gate D003 can meet on day one rather than a risk it must resolve. And **implement rendered-to-source resolution as run-atomic wherever a run's rendered and source lengths differ**, per the constraint derived in section 2: record the two lengths (or the run kind) in the map, interpolate only when they agree, and resolve any offset inside a non-length-preserving run to that run's whole source range rather than to an interior byte. D003's fixture corpus for the two offset-resolution Gherkins must include an inline code span, a named entity (`&amp;`, `&eacute;`), a numeric reference (`&#65;`), a backslash-escaped delimiter and an inline link — the last two because their run source ranges do not tile the Block, so any implementation that reconstructs a selection by concatenating run sources fails on them even though interpolation does not. `hello **bold** world` alone passes against a broken implementation.

### 6.2 Tier 2 timer synchronization: decided

**Historical supersession — 2026-08-23, PR #10 review round 4:** This section
records the original three-lock measurement. The per-Note tier 1 mutation lock
was added after that measurement. ADR-008 v1.6.1 defines the current five-lock
order and the tier-1 rollback and lifecycle-installation rules.

The tier 2 timer synchronizes with the synchronous FFI calls through **a per-Note state lock that no thread ever holds across I/O, over a working source stored as `Arc<String>` and mutated through `Arc::make_mut`** — plus a second, separate lock that serializes tier 2 writers against each other and which no keystroke can ever contend for. The governing rule is not "no lock is held across I/O", which is unachievable once two writers can target one file; it is **no lock that an FFI call on the Dart thread must acquire is ever held across I/O**. Concretely, and this is the shape `BURL-D007` implements:

1. **Three locks, with a total acquisition order.** Per open Note: a **state lock** guarding {working source `Arc<String>`, span map, edit sequence, recorded revision}, and a **tier 2 write lock** guarding the act of writing that Note's file. Process-wide, unchanged: `db::connection`'s `Mutex<Connection>`, which stays exactly what it is today, a serializer admitting one statement at a time. The only permitted acquisition order is **tier 2 write lock, then state lock, then connection**, and no two of them are ever held simultaneously except the tier 2 write lock over the state lock, for the duration of a snapshot. Since the keystroke path acquires only state and then connection — a suffix of that order — no cycle exists and deadlock is unrepresentable rather than merely unobserved.
2. **`update_block`, on the Dart caller's thread:** acquire the state lock; `Arc::make_mut` the buffer and substitute the new Block source; move the edited span's end by the byte delta and shift every later span by the same delta (ADR-008 decision 2); **increment the edit sequence** and take an `Arc::clone` of the buffer together with the new sequence value; **release the state lock**; then acquire the connection and write the tier 1 draft row from the snapshot, storing that sequence value in the row. The increment happens exactly here — under the state lock, in the same critical section as the buffer mutation — and in every other tier 1 mutator ADR-008 decision 1 lists (`insert_block`, `delete_block`, `split_block`, `merge_block_with_previous`, `delete_range`, `replace_range`, `resolve_suggestion`), each of which changes content and writes a row. It happens nowhere else.
3. **`commit_block`, on the Dart caller's thread:** acquire the state lock; `Arc::clone` the buffer and read the edit sequence; **release the state lock**; reparse the snapshot and build the new span map holding no lock at all — this is the 3.4ms-at-102 KiB operation of section 4.1, far too long to hold a lock the timer needs; then re-acquire the state lock, and install the new map only if the edit sequence is unchanged, redoing the reparse if it is not. Under FRB, `#[frb(sync)]` calls for one Note are serialized on the Dart caller's thread and the timer never mutates the buffer, so the retry should never fire; it is written as a check rather than an assumption because the cost is one integer comparison and the failure it would otherwise hide is a span map describing a buffer that no longer exists. **`commit_block` must not increment the edit sequence.** It writes no draft row (ADR-008 decision 1 makes it the sole mutator that does not), so an increment here would advance the counter past the value stored in the row and suppress a legitimate tier 2 clear for the rest of the session.
4. **The tier 2 timer, on its own Core thread:** acquire the tier 2 write lock; acquire the state lock; `Arc::clone` the buffer, read the edit sequence and the recorded revision; **release the state lock**; perform the OCC check and the atomic file write from the snapshot holding only the tier 2 write lock; then acquire the connection and clear the draft row conditionally; re-record the revision; release the tier 2 write lock. The same sequence, under the same lock, is what `close_note` and application quit run when they flush tier 2 before tier 3.
5. **The tier 2 write lock exists because tier 2 has more than one writer, and it does not reintroduce the shape rejected in section 5.** ADR-008 fires a tier 2 write from the idle timer *and* from `close_note` — "switching away from a Note is a close, and must flush tiers 2 and 3" — so two tier 2 writes for one Note can be in flight at once. Two obligations follow. First, the temporary file must be **uniquely named per write** rather than derived from the target: this Spike's own prototype used a fixed `target.with_extension("tmp")`, which two concurrent writers would share, and the loser would rename a partially-written file over the Note. Second, and more seriously, `BURL-D007`'s Optimistic Concurrency Control — compare the on-disk hash against the Core's recorded revision immediately before writing, re-record after a successful write — is a time-of-check-to-time-of-use bug unless one lock spans check, write and re-record as a unit; without it, two writers both read the same revision, both pass, and the second silently discards the first. The tier 2 write lock spans exactly that sequence. It **is** held across the file write, and that is deliberate and safe: it is taken only by tier 2 writers, never by `update_block` or `commit_block`, so no keystroke can ever wait on it. The property section 4.4 measures — that no lock a keystroke needs is held across I/O — is preserved exactly.
6. **The draft-clear must be conditional, and must fail toward keeping the row.** ADR-008 tier 1 says a successful tier 2 write clears the draft row, which is sound only if the row holds the bytes just written to disk. An earlier revision of this section proposed comparing an in-memory edit counter under the state lock, and that is wrong in a way that loses data on the *likely* interleaving rather than a rare one: `update_block` releases the state lock before its 8-23ms row write, so a timer that snapshots at sequence N, writes the file, re-acquires and observes the counter still at N would clear a row that the keystroke is about to write — and then the keystroke writes row(N) into a table the timer believed it had emptied. The counter to compare is therefore **not the buffer's; it is the row's**. The sequence value is persisted into the drafts row by the tier 1 write (6.2.2), and the timer's clear is a single conditional statement executed under the connection mutex — `DELETE FROM drafts WHERE note_id = ?1 AND edit_seq <= ?2`, bound to the snapshot's sequence — so "clear" means "the row holds nothing newer than what is now on disk", evaluated atomically against the row itself rather than against a counter that leads it. `<=` rather than `=` because a row lagging the snapshot is also redundant once the newer bytes are on disk, and refusing to clear it would leave `open_note` preferring an older draft over a newer file. The residual case is benign and must be stated so it is not mistaken for a defect later: if the keystroke's row write lands *after* the DELETE, the row survives holding bytes identical to disk, which is a false "restored from draft" rather than a loss. It is cleared by the next timer firing, and unconditionally by tier 3 on close. **The asymmetry is the point: failing to clear costs one spurious recovery notice, clearing wrongly costs the user's work, so every ambiguous case must resolve toward keeping the row.**
7. **The standing review rules this implies:** no closure passed to `with_connection` may perform file I/O; no lock a keystroke can contend for may be held across an `fsync`; and no tier 2 write may be issued outside the tier 2 write lock. All three are trivially true today and all three are exactly what a tier 2 implementation would break first.

Measured result of this shape (section 4.4): the tier 2 side holds the state lock for a median, p95 and maximum of 0.000, 0.000 and 0.001ms at both 102 KiB and 1 MiB, and the keystroke's own buffer-and-span work never waits — 0.031ms and 0.336ms p95 respectively, against 1.487ms and 10.397ms under the naive shape at the same settings, and 55.947ms under the naive shape at SQLite's defaults. The tier 2 write lock added in 6.2.5 is not represented in those measurements, which modelled a single tier 2 writer; it cannot change them, because no thread that takes it is one whose latency the table reports. The residual serialization between the keystroke's tier 1 write and the timer's draft-clear is one statement on the connection mutex, which is inherent to having one connection and is not what ADR-008 was worried about.

### 6.3 A finding that requires production changes, and the tickets that must make them
This Spike performs no production changes. Two are required by its findings and are named here rather than made:

- **`BURL-D007` (Persistence Tiers) owns the tier 1 cost problem.** ADR-008 tier 1 describes itself as cheap. Measured against the encrypted index on real storage with content that actually changes, writing the full working source per keystroke costs 7.96ms at 102 KiB and 22.79ms at 1 MiB — at 1 MiB, over budget before any other work is counted, and the dominant term in every row of section 4.4. D007 must treat this as its own acceptance concern; the spike's contribution is the number, the demonstration that the buffer and span work around it is three orders of magnitude smaller, and the warning that any benchmark rewriting a constant string will report 0.22ms and be wrong by a factor of 36.
- **`BURL-D004` (Local Workspace Bootstrap) owns the connection pragmas, and the benefit is real but narrower than a single number suggests.** It already scopes `rust/src/db/connection.rs` and `db/schema.sql`, and `guidelines.md` already states connection-time obligations there (`PRAGMA foreign_keys = ON` after the key pragma, `user_version` read before write), so `journal_mode = WAL` with `synchronous = NORMAL` belongs in the same place rather than being improvised by D007. What it buys is **size-dependent and is mostly a small-Note effect**: at 102 KiB the standalone measurement gives 3.3x (7.96ms to 2.41ms) and the contention runs give about 2.3x (roughly 6.2-7.6ms to 2.7ms), while **at 1 MiB it is worth little to nothing** — 22.79ms to 16.14ms standalone (1.4x), and section 4.4's own contention rows show 24.4ms under WAL against 23.1-24.9ms without it, which is no benefit at all. The mechanism explains the shape: WAL removes the rollback journal's double write and two of three per-commit `fsync` calls, both of which are largely fixed costs, so they dominate a small write and are swamped by the encryption and page-write volume of a large one. Adopt it because it is free, correct and helps the common case; do not adopt it as a fix for the tier 1 cost in the bullet above, which it does not solve at the sizes where that cost actually hurts. WAL still `fsync`s at checkpoint, so `NORMAL` costs at most the last commits on an unclean power loss, never integrity — and tier 1's purpose is to survive an application crash, which WAL handles unconditionally.

## 7. Downstream Backlog Impact
- **`BURL-D003` (Span-Preserving Parse and Splice Engine) is unblocked**, with its strategy fixed: reparse after every committed splice, span map built in the parse pass, no offset arithmetic on any committed path, no size threshold, and the round-trip property as the primary gate. It also inherits one constraint this Spike did not expect to find — rendered-to-source resolution must be run-atomic wherever a run's rendered and source lengths differ (section 2, restated as an obligation in 6.1), and its fixture corpus for the two offset-resolution Gherkins must cover code spans, entity references, escapes and inline links. Through this ticket, the whole of Epic D's write path is unblocked.
- **`BURL-D007` (Persistence Tiers) is informed and constrained**: the lock shape in 6.2 is decided, including the tier 2 write lock and unique temp-file naming in 6.2.5, the OCC check that lock must span, the conditional row-scoped draft-clear in 6.2.6, and the rule that ambiguity resolves toward keeping the draft row. The tier 1 write cost in 6.3 is its problem to carry.
- **`BURL-D004` (Local Workspace Bootstrap) is informed**: the WAL and `synchronous` pragmas belong with the other connection-time obligations it already scopes, with the size-dependent benefit stated in 6.3 so they are not mistaken for a fix to the tier 1 cost.
- **`BURL-D008` (Editing FFI Surface) is informed**: `update_block` must follow the acquire-mutate-bump-snapshot-release-then-write ordering in 6.2.2 and `commit_block` the reparse-off-lock ordering in 6.2.3, including that `commit_block` does not advance the edit sequence. Being `#[frb(sync)]` is exactly what makes a held lock a stalled frame.
- **No STOP condition fired.** Whole-file reparse meets the 16ms budget at realistic Note sizes with margin, so ADR-007's mitigation stands and no Stage 3 pass is required. The tier 2 timer's synchronization is decided here rather than deferred, with the contention measured under four lock shapes and two database configurations. This Spike lands in exactly one commit touching no file under `rust/src`.
