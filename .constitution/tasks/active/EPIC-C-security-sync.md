# Epic C: Security & Sync

#### SYNC-C001 Implement Git Operations (gix)
- **Type:** Feature
- **Effort:** 8
- **Dependencies:** UIDB-B004
- **Category:** Correctness
- **Scope (In-Scope Files):**
  - `rust/src/git/operations.rs`
- **Description:** Implement programmatic Git `clone`, `commit`, `push`, and `pull` operations against the local Workspace directory using `gix` (or shelling out to the `git` CLI if `gix` currently lacks robust working tree merge conflict generation).
- **Acceptance Criteria (Gherkin):**
```gherkin
Given a local directory with changes
When the commit function is called
Then `gix` successfully creates a Git commit in the local `.git` index
```

##### SYNC-C001 Deviations & Justifications
- **Touched Files:**
  - `rust/src/git/operations.rs` (in scope) — `clone_repo`, `commit_all`, `push`, `pull`, and the `GitCredentials` auth wiring point.
  - `rust/src/git/mod.rs` (new) — declares `pub mod operations;`; `git/` already existed as a directory name in `guidelines.md`'s documented layout but had no `mod.rs` yet.
  - `rust/src/lib.rs` — added `pub mod git;` so the new module is reachable; every other top-level module (`api`, `db`, `markdown`, `security`) is wired the same way, so this follows existing convention rather than deviating from it.
  - `rust/Cargo.toml` / `rust/Cargo.lock` — added `gix = "0.86.0"` with `default-features = false` and an explicit feature list (`max-performance-safe`, `sha1`, `blob-diff`, `revision`, `index`, `excludes`, `worktree-mutation`, `credentials`, `interrupt`, `tree-editor`, `blocking-network-client`, `blocking-http-transport-reqwest-rust-tls`) — the minimal set covering clone (with HTTPS transport, for eventual GitHub remotes), commit/tree-editing, and index read/write, verified by `cargo check` against gix 0.86.0.
  - `.constitution/tech-spec/stack.md` — corrected the "Git Implementation" line to describe the verified gix/git-CLI hybrid instead of just "`gix` (gitoxide)".
  - `.constitution/tech-spec/changelog.md` — new `v1.0.3` entry recording the same correction with its justification.
- **Justification:** The ticket's scope line names only `rust/src/git/operations.rs`, but a new module cannot compile or be reachable without `mod.rs` + a `lib.rs` wire-up, and a new crate dependency cannot exist without `Cargo.toml`/`Cargo.lock` changes — these are mechanical consequences of the in-scope file existing at all, not scope creep. The `stack.md`/`changelog.md` edits are required by the "Spec honesty" rule: this ticket's actual, verified design is a gix/git-CLI hybrid (gix has no push support at all, and its merge support does not yet cover commits — see the capability findings in `rust/src/git/operations.rs`'s module doc comment), which is materially different from the stack's original single-word "`gix` (gitoxide)" claim.

#### SYNC-C002 Implement OAuth Handshake
- **Type:** Feature
- **Effort:** 5
- **Dependencies:** UIDB-B005
- **Category:** Security
- **Scope (In-Scope Files):**
  - `lib/src/screens/login.dart`
  - `rust/src/api/auth.rs`
- **Description:** Build the OAuth web flow in Flutter to capture a GitHub authorization code, pass it to Rust, exchange it for tokens via PKCE, and store them via `keyring`.
- **Acceptance Criteria (Gherkin):**
```gherkin
Given the Login screen
When the user completes the OAuth flow
Then the Access Token is securely stored in the OS Keychain by Rust
```

##### SYNC-C002 Deviations & Justifications
- **Touched Files:**
  - `rust/src/api/auth.rs` (in scope) — new module: PKCE generation, GitHub authorize-URL construction, token exchange, and OS-Keychain storage, plus the `begin_oauth_flow`/`authenticate_workspace` `#[frb]` wrappers.
  - `lib/src/screens/login.dart` (in scope) — new `LoginScreen` (`ConsumerWidget`), stateless regarding flow state per `guidelines.md`.
  - `rust/src/api/mod.rs` — added `pub mod auth;`, the same mechanical wiring precedent as SYNC-C001's `pub mod git;`/`pub mod operations;`.
  - `rust/Cargo.toml` / `rust/Cargo.lock` — added `reqwest` as a *direct* dependency (`blocking`, `rustls`, `json`, `form` features; already present transitively via `gix`'s `blocking-http-transport-reqwest-rust-tls`, per the design decision to reuse it rather than add a second HTTP crate) for the token exchange and `GET /user` calls; `sha2` (S256 PKCE challenge, RFC 7636); `base64` and `url` (already transitively resolved via `reqwest`, promoted to direct); `serde`/`serde_json` (token-response parsing). Also added `ctor` as a **dev-only** dependency, to close a real race in `keyring` 4.1.5's lazy default-store initialization that this ticket's own (more numerous, now-concurrent) keyring tests exposed — see `rust/src/api/auth.rs`'s `new_keyring_entry` doc comment for the full account.
  - `rust/src/frb_generated.rs`, `lib/src/rust/api/auth.dart`, `lib/src/rust/frb_generated.dart`, `lib/src/rust/frb_generated.io.dart`, `lib/src/rust/frb_generated.web.dart` — regenerated by `flutter_rust_bridge_codegen generate` after adding the new Rust FFI surface, per the ticket's own instructions. Mechanical, not hand-edited.
  - `.constitution/tech-spec/contracts/ffi_api.rs` — mirrored the `begin_oauth_flow`/`OAuthFlowStart` addition (required by the ticket: this ticket adds a function beyond the existing contract, and the contract must reflect it).
  - `.constitution/tech-spec/changelog.md` — new `v1.0.4` entry recording that addition, the `client_secret`-is-required-even-with-PKCE correction (see below), and the `workspaces.id`-minting decision.
  - `lib/src/providers/rust_api_provider.dart` — added `beginOAuthFlow`/`authenticateWorkspace` methods to the existing `RustApi` seam (the same pattern `openNote`/`searchNotes`/etc. already follow), so `login.dart` and its tests go through the same override-able boundary as the rest of the app instead of importing generated FFI bindings directly.
  - `lib/src/providers/auth_provider.dart` — new file: `AuthStatus`/`AuthFlowState`/`AuthController`/`authControllerProvider`, the Riverpod state machine driving the login screen (design decision #6 explicitly calls for Riverpod-based flow state "consistent with `lib/src/providers` patterns" — `note_providers.dart` establishes the one-provider-file-per-concern convention this follows).
  - `lib/main.dart` — least-invasive login gate: `MyApp` now shows `LoginScreen` unless `authControllerProvider` is `AuthStatus.success`. Explicitly pre-approved in the ticket's own scope-deviation allowlist; documented in-file as a real limitation (no "already authenticated from a prior session" check exists, since no such FFI call is in the contract — every process restart re-shows `LoginScreen` even if a token from an earlier session is still sitting in the OS Keychain).
  - `pubspec.yaml` / `pubspec.lock` — `url_launcher` added via `flutter pub add url_launcher` (runtime dependency, per the ticket's explicit instruction to use the CLI); `url_launcher_platform_interface` and `plugin_platform_interface` added via `flutter pub add --dev` (test-only, to fake the browser-launch platform channel in `test/providers/auth_provider_test.dart` without a real OS browser).
  - `linux/flutter/generated_plugin_registrant.cc`, `linux/flutter/generated_plugins.cmake`, `macos/Flutter/GeneratedPluginRegistrant.swift` — auto-regenerated by the `flutter pub add` CLI run to register `url_launcher`'s platform implementation for the desktop targets already in scope (`stack.md`). Not hand-edited.
  - `test/widget_test.dart` — wrapped `MyApp` in a `ProviderScope`: `MyApp` now transitively reads `authControllerProvider` via `_Home`, so the existing test needs the same Riverpod ancestor every other widget test in this repo already provides.
  - `test/screens/login_test.dart`, `test/providers/auth_provider_test.dart` — new test files for the Gherkin/TDD coverage the ticket calls for.
- **Justification:** The ticket names only two in-scope files, but (a) a new Rust module cannot be reachable without a `mod.rs`-equivalent wire-up and a new crate dependency cannot exist without manifest changes (mechanical consequences, same precedent as SYNC-C001); (b) the ticket's own instructions explicitly require mirroring the new FFI function into the contract/changelog and regenerating+committing FRB bindings in the same commit; (c) a Riverpod-driven login screen cannot exist without a provider to hold its state, and cannot be wired into `main.dart` without touching `main.dart` — both explicitly pre-approved in the ticket's deviation allowlist; (d) `url_launcher` was required by name in the design decisions, and `flutter pub add` mechanically touches `pubspec.{yaml,lock}` plus the desktop plugin registrant files as an unavoidable side effect of using the CLI (which the project's own global rules mandate over hand-editing).
- **Spec drift corrected:** Design decision #5 assumed "PKCE on a public client" eliminates the need for a `client_secret`. Verified against GitHub's current OAuth documentation (2026-07-24): the access-token exchange's parameter table lists `client_secret` as "Required" with no PKCE exception, for both classic OAuth Apps and GitHub Apps — a wrong/missing secret fails with `incorrect_client_credentials` regardless of a correct `code_verifier`. PKCE is additive defense-in-depth against authorization-code interception on GitHub's implementation, not a substitute for the secret. `rust/src/api/auth.rs` reads an optional secret from `BURLMD_GITHUB_CLIENT_SECRET` at runtime (never hardcoded, never committed) so the real exchange can still succeed once a GitHub OAuth App/GitHub App is registered; see the module's doc comment for the full citation trail.

#### SYNC-C003 Background Sync Manager Scheduler
- **Type:** Feature
- **Effort:** 3
- **Dependencies:** SYNC-C001, SYNC-C002
- **Category:** Correctness
- **Scope (In-Scope Files):**
  - `rust/src/sync/scheduler.rs`
- **Description:** Implement a debounced background worker in Rust that calls the `gix` push/pull operations automatically every X minutes or after explicitly saving.
- **Acceptance Criteria (Gherkin):**
```gherkin
Given active local commits
When 5 seconds of inactivity pass
Then the background worker automatically pushes to the Remote Repo
```
