**Three decisions carried forward, recorded here so the ticket that first needs them does not rediscover them.**

1. **`workspaces ON DELETE CASCADE` would strand `notes_fts` rows.** Deleting a `workspaces` row cascades to `notes`, which cascades to `fts_mapping` — but `notes_fts` is an FTS5 virtual table that no foreign key reaches, so its rows survive with nothing left pointing at them. `delete_note` and `delete_directory` avoid this by clearing the FTS row explicitly, first, in the same transaction; a workspace-level delete has no such path. The candidate fix is a `BEFORE DELETE` trigger on `workspaces`, which needs a `PRAGMA recursive_triggers` check first, since cascaded deletes do not fire triggers by default. **Deferred to the ticket that first deletes a `workspaces` row** — no code path does today.
2. **`SpliceError` collapses to `AppError::ParseError`.** `workspace::persist::splice_error` maps every `SpliceError` variant — `UnknownBlock`, `OffsetOutOfRange`, `InvertedRange`, `InvalidSourceRange` — onto one contract variant. These are caller errors (a stale `block_path`, an out-of-range selection), not parse failures, and `ParseError` is merely the nearest variant the contract offers. **Epic F's error-presentation work should discriminate them**, since "a Block moved under you, re-derive the path" and "this selection is invalid" call for different UI.
3. **Post-pull incremental indexing has no entry point.** `index::incremental::index_note` handles one Note at a time and returns `NotFound` for a file that has vanished, so there is neither a batch entry point over a changed-path set nor an incremental *removal* route. A pull that deletes or renames files therefore has no way to bring the index level short of a full `reindex_workspace`. **Owned by the ticket that wires `SyncDeps::reindex`.**

**Two interpretations recorded during PR #7 review, both filling a silence in `contracts/ffi_api.rs` rather than changing it.**

- **`create_note` requires the Directory named by `directory_path` to already exist**, and returns `PathUnavailable` when it does not. The contract says nothing either way, and the two functions that take a Directory had drifted apart: `move_note` refuses an unknown destination, while `create_note` was calling `create_dir_all` over the whole hierarchy — so one typo in `SHEL-E005`'s field silently created a Directory and filed the Note out of sight inside it, with no signal and nothing to undo. Settled toward the stricter and already-contracted reading, so both entry points onto a Directory answer identically and `create_directory` is the single explicit route to a new level. An empty `directory_path` remains the bundle root and is unaffected.
- **`NoteWriteStatus` cannot report a transient tier 2 failure, and extending it is a Stage 3 change.** `note_write_status` is a poll, and a successful write clears `last_error`, so any failure that occurs and then resolves between two polls is invisible to the UI — the recovery notice `SHEL-E007` is meant to raise never fires for exactly the intermittent case (a full disk that drains, a file locked by a sync) it would be most useful for. Deliberately **not** fixed in the review round that found it: `NoteWriteStatus` is a contract type and adding a field is an amendment here, not an implementation detail. **`SHEL-E007` should amend `NoteWriteStatus` first** — with a failure counter, or a `last_error_at` the UI can compare against its previous poll — before building the notice on top of the poll as it stands.

**Two further findings recorded during PR #7 review round 5, both deliberately left for Epic E to settle rather than fixed here.**

- **Concurrent commits can lose the HEAD ref CAS.** Two tier-3 closes, or a close racing a lifecycle commit, both go through `git::operations::commit_paths`, which reads `HEAD`, builds a tree from it and compare-and-swaps the ref — so the loser fails, and the same window puts two writers on `.git/index.lock`. Nothing serializes them today because nothing dispatches more than one at a time; **the Epic E shell ticket that dispatches close-on-quit must serialize `commit_paths` or bounded-retry it**, since quitting with several Notes open is exactly the moment that fans out.
- **Discovery and the tree fold case differently.** The discovery queries fold ASCII-only (SQLite `NOCASE`) while `index::query`'s tree folds full Unicode (Rust `to_lowercase`), and `LIKE`'s prefix match is ASCII-only too — so `über` does not find `Über` in `find_notes_by_title` or `link_completions` while the tree sorts them as if it did. **The Epic E palette ticket should pick one collation — most likely a custom SQLite collation registered on the connection — before either surface is exposed to keystrokes**, because changing it afterwards changes indexed comparison semantics.
- **Re-opening the active Workspace mid-session can transiently drop freshly-written rows.** `workspace::bootstrap`'s converge scans the bundle and then rebuilds the index unconditionally, so a tier-2 write that lands between the scan and the rebuild is discarded from the index while its bytes stay on disk — self-healing at the next tier-2 write for that Note, and not data loss, but a window in which the tree and search disagree with the bundle. **The Epic E shell should either prevent re-opening the Workspace that is already active, or the scan should be taken under the tier-2 write locks; that ticket decides which** — found in PR #7 review round 8 and deliberately not restructured there.

**Four further records from PR #7 review round 9.** Two are decisions filling a silence, one narrows an item recorded above, one is a follow-up owned by an existing Epic E ticket.

- **The Link read path deliberately does not percent-decode a destination, and that asymmetry is intended.** `data-models/okf-bundle.md` rejects percent-encoding on the *write* side and gives the reason (a title legitimately containing `%` — `100% Done` — decodes to something the user never wrote, so `target_id` derivation would be lossy); the read side simply never decodes, so a foreign bundle's `[a](/Plan%20A.md)` derives the concept id `Plan%20A` and classifies as a ghost Link rather than resolving to `Plan A`. That is the correct behaviour under path-based identity — the id *is* the path as written — and it is recorded here so it is not "fixed" as an oversight. **CAP-PORT-03's foreign-bundle expansion may revisit it**, since a decode-on-read-only rule is expressible (decode for resolution, never for storage) at the cost of the ambiguity the write-side rejection avoids.
- **A file or directory name that is not valid UTF-8 is a documented skip rule.** `index::scan::walk_bundle` used `to_string_lossy` on every entry name, which does not fail — it substitutes `U+FFFD` — so a non-UTF-8 `.md` filename minted a concept id that named no file and the Note vanished from the index with no row and no signal, while a non-UTF-8 *directory* name recorded a `directories` row nothing could address and took its whole subtree with it. Both are now skipped outright, alongside the existing dot-prefixed and symlink rules, and the walker documents why. The bytes on disk are untouched; this governs what the index covers.
- **The HEAD-ref-CAS item above is now narrower than it was written.** Round 9 gave every `workspace::lifecycle` entry point a Workspace-level lifecycle mutex (create/rename/move/delete Note, create/rename/delete Directory), taken above the tier-2 write locks and held for the whole operation including its commit — so two *lifecycle* commits in one Workspace can no longer race each other, and neither can two lifecycle operations pass the same `ensure_path_available` check. What the round-5 item still describes correctly, and what the Epic E ticket still owns, is **tier-3 close against tier-3 close, and close against a lifecycle commit**: `NoteSession::close` deliberately takes no lifecycle lock, because putting a `git` commit's latency on the editing path is the trade ADR-008's lock discipline exists to avoid.
- **`workspace_tree` rebuilds the whole tree on every call**, and should be measured by the same Epic E ticket that measures `find_notes_by_title`'s unindexed prefix scan (see the `contracts/ffi_api.rs` note above). Both are per-call O(Workspace) work on a discovery surface that a shell may poll or drive from keystrokes; neither is a correctness problem, and neither has a number attached to it yet.

**Two further records from PR #7 review round 11, both deliberately left as they are.**

- **`ScratchSweep`'s result is unreachable in production.** `workspace::bootstrap`'s sweep returns a structured count of what it removed and what it could not, and its own documentation says that is "the only place" the outcome exists — but nothing in the running application reads it, because this crate has no logging channel to put it on. A bundle whose scratch files cannot be removed (a read-only mount, a permission the user changed) therefore sweeps silently on every open with no trace. **Owned by the logging-gap follow-up**, which is what will give this and every other Core-side diagnostic somewhere to go; the struct is deliberately kept rather than collapsed to a `()`, so that surfacing it later is a wiring change and not a rewrite.
- **The bundle walkers recurse without a depth bound.** `index::scan::walk_bundle` and `workspace::lifecycle`'s directory collectors descend by recursion, so a pathologically nested bundle is bounded only by the stack. In practice `PATH_MAX` gets there first — every level adds at least two bytes to a path the walker must be able to open — and no bundle burlmd writes nests beyond a handful of levels. Recorded rather than fixed: an explicit depth cap is a policy about what a bundle may contain, which belongs with CAP-PORT-03's foreign-bundle rules rather than in a walker. **Revisit if a bundle ever nests pathologically**, or if the walkers gain a caller that is not a user-driven bootstrap.

**Two further records from PR #7 review round 14.** One settles a silence in the same place the percent-decoding item above settles one; the other is a known optimization deliberately not taken inside a review loop.

- **A fragment-bearing destination is not a Note reference, on either side of the read path, and that is now consistent.** `okf::links::classify` tests the destination exactly as written, so `Other.md#section` does not end in `.md` and reports **External** — the same no-decoding-on-read stance the percent-encoding entry above records, reached by the same reasoning. `resolve_bundle_path` disagreed for the one operation that consults it: `absolutize_relative_links` resolved the fragment as part of a *path*, so moving a Note rewrote `[a](Other.md#section)` to `[a](</sub/Other.md#section>)` — half-recognizing a reference nothing else in the crate recognizes, and treating `Other.md#section` as a filename. Settled toward `classify`: a `#` anywhere in the destination now stops `resolve_bundle_path`, so a move leaves such a link byte-for-byte alone. **This is the same CAP-PORT-03 revisit as the percent-decoding item** — a foreign-bundle expansion that teaches `classify` to split a fragment off before testing the extension must teach `resolve_bundle_path` the same split, in one change rather than two, or the two halves drift apart again in the other direction.
- **`workspace::lifecycle::plan_affected` issues O(N) database round-trips per Directory rename.** It calls `link_sources` once per remapped id and `read_draft_text` once per candidate, each its own `with_db` acquisition of the process-wide connection mutex, so renaming a Directory holding N Notes costs on the order of 2N short queries rather than a constant number of batched ones. Correctness is unaffected and no Workspace has been measured slow here. **Batching both through `IN`-lists is the known optimization if Directory renames ever profile slow**; deliberately not done in the review loop, where restructuring the one function every re-identification runs through buys no correctness and risks the sweep-population invariants that three rounds of fixes established.

**Three further records from PR #7 review round 15.** One shares its root cause with the `workspaces ON DELETE CASCADE` item numbered 1 above; the other two are Dart-side hardening owed by Epic E tickets that do not exist yet.

- **`notes_fts` has no `workspace_id` column, so search is scoped after the match rather than during it — and that shapes the ranking, not just the cost.** This is the same root cause as the `workspaces ON DELETE CASCADE` item above (item 1 of the three carried forward): FTS5 cannot express a foreign key or a composite key, so `fts_mapping` carries the Workspace identity on the virtual table's behalf and `notes_fts` itself holds only `(title, content)` for every Workspace on the machine. `SEARCH_NOTES_SQL` therefore drives from `notes_fts MATCH ?1` across the whole index and narrows to one Workspace by joining `fts_mapping` afterwards, with two consequences worth recording before anyone reads a relevance ordering as a per-Workspace fact. First, **bm25 statistics derive from the entire index**: term frequencies and document lengths are computed over every Workspace's rows, so the order two hits come back in within one Workspace is influenced by text in Workspaces the user is not searching — adding a large unrelated Workspace can reorder results in a small one without either one changing. Second, the pre-`LIMIT` scan is proportional to the whole index rather than to the Workspace, so a user with many Workspaces pays for all of them on every keystroke-driven search. Neither is a correctness defect and the shipped query plan is already the pinned, measured one (`SCAN notes_fts` → `SEARCH fts_mapping` → `SEARCH n`); what is deferred is whether to make the Workspace part of the *indexed* text — an external-content FTS5 table, a per-Workspace `notes_fts` instance, or a column-filtered `MATCH` — each of which changes both the deletion ordering obligation `schema.sql` documents and the migration story. **Owned by the same ticket that resolves the cascade item**, since both are answers to "what does `notes_fts` know about a Workspace".
- **The Dart discovery wrappers pass an unclamped `int` into a Rust `u32`.** `searchNotes`, `findNotesByTitle` and `linkCompletions` in `lib/src/providers/rust_api_provider.dart` take `int limit` and hand it straight to the generated FFI binding whose Rust side is `u32`, so a negative value does not fail — it wraps, and `-1` arrives as `4294967295`, i.e. an effectively unbounded query on the surface the `limit` parameter exists to bound. Today every caller passes a literal, so nothing can produce one. **The Epic E palette ticket is where that stops being true** — a limit computed from viewport height, a page size, or a remaining-budget subtraction is exactly the arithmetic that goes negative at the edges, and it lands on the keystroke path. Clamp in the wrappers (reject or floor at zero) when that ticket puts a computed value there, rather than relying on every future call site to have checked.
- **`NoteController.open` assigns state after an `await` with neither a staleness guard nor an error path.** In `lib/src/providers/note_providers.dart` (the class the review round referred to as `NoteOpener`), `open` awaits `openNote(noteId)` and then assigns the result to `state` unconditionally: two opens in flight resolve in completion order rather than call order, so a slow first open can overwrite a fast second one and leave the editor showing a Note the user has already navigated away from, and a rejected future — `NotFound` for a Note deleted out from under the shell, or any I/O failure — propagates out of an unawaited `Future<void>` with the UI still showing the previous Note and no signal. Both are latent for the same reason as the item above: nothing dispatches concurrent or failing opens today. **Owed by the Epic E shell ticket that starts driving it** — a request id compared before the assignment, and a caught error surfaced into the provider's state rather than discarded — recorded here so that ticket does not have to rediscover that the guard is missing.

## v1.1.0
Evolution pass consuming PRD v1.1.0 and this session's pre-Tasks interview. Minor bump: five ADRs, a new storage-format contract, and a materially expanded FFI surface, with no reversal of a prior stack selection.

The pass was triggered by a finding that Stage 4 could not proceed: too much of what the next epics need did not exist at this layer, and `planning-engineering-execution` forbids inventing contracts. The largest gaps were that the project's own on-disk format was never specified, and that the FFI contract had no function for creating, deleting, renaming, or listing a Note.

**ADR-004 — OKF v0.2 conformance.** Investigation established that "Open Knowledge Format", named in `prd/vision.md` since v1.0.0 but never defined anywhere downstream, is a real published specification (Google Cloud, announced 2026-06-12, `GoogleCloudPlatform/knowledge-catalog`, `okf/SPEC.md`), currently at v0.2. Pinned to v0.2. Its §2 settles Note identity as the bundle-relative path with `.md` removed, which authoritatively resolves a question this project had answered inconsistently in three places. Its §11 conformance rules are only three and all cheap. The costs accepted — a frontmatter block on every Note that the primary actor now sees constantly, and verbose bundle-absolute link targets in raw view — are recorded in the ADR and in `prd/out-of-scope/wikilink-syntax-on-disk.md`.

**ADR-005 — local-first Workspace, opt-in Remote.** The application is currently unusable: `lib/main.dart` gates everything behind a login screen, and Epic C deferred item 1 means no OAuth App is registered, so the gate cannot be passed at all. The cause is a specification error rather than a coding error — OAuth was the only documented path to a Workspace. Workspaces are now initialized locally with `provider = 'local'` (a value `schema.sql` has carried since v1.0.0 and no code has ever used), with `init` rather than `clone`, and with the root encryption key generated during bootstrap rather than inside the OAuth handshake.

**ADR-006 — raw-on-focus editing.** Records how CAP-EDIT-01 (focused Block shows raw source) and CAP-EDIT-04 (selection spanning Blocks) are satisfied simultaneously without the Presentation Container becoming an owner of note content. Rendered Blocks sit inside one `SelectionArea`; focus promotes exactly one Block to a plain editable field; multi-Block range operations dispatch to Rust. Verified against Flutter's `SelectableRegion` documentation, which specifies the `Selectable` mixin and `SelectionRegistrar` registration and confirms `Text` participates automatically — the docs are silent on whether `EditableText` participates, and the design deliberately does not depend on it. `appflowy_editor` 6.2.0 and `super_editor` 0.2.7 were both evaluated and rejected, on architectural grounds and on maintenance/Linux-support grounds respectively; the reasoning is recorded so it is not silently revisited.

**ADR-007 — span-preserving source splicing.** The single largest change. `flow-edit-note.md` had specified serializing the AST back to Markdown; PRD v1.1.0's Edit Fidelity constraint makes that unusable, since a serializer rewrites the whole file by definition and nothing ever specified a canonical form for it to write. Editing being raw means the editor already holds the bytes belonging in the edited Block's span, so saving becomes a splice. Verified in the vendored source that `pulldown-cmark` 0.12.2 provides both required APIs — `Parser::into_offset_iter()` at `src/parse.rs:1310` and `Options::ENABLE_YAML_STYLE_METADATA_BLOCKS` at `src/lib.rs:559` — rather than assuming them. Consequences: no serializer exists on the save path by design; `update_block` changes from taking an `AstNode` to taking source text; spans live Core-side keyed by `block_path` and never cross the FFI boundary; and `base_revision` becomes a content hash, which fixes an open→save path that was broken by construction (`open_note` returned the literal `"head"` while `save_note` compared a stringified `notes.last_modified`).

**ADR-008 — four-tier persistence.** Keystroke to the `drafts` table, ~1s idle to an atomic file write, Note close to one Git commit, commit to `notify_activity()`. Commit-on-close rather than on a timer, so history reads as one entry per Note per sitting. This gives the `drafts` table its first reader and writer and `SyncScheduler::notify_activity()` its first caller — both have existed with neither since their respective epics. The accepted cost is that a Note left open for hours is written but uncommitted, and therefore unpushed.

**New: `data-models/okf-bundle.md` and `data-models/okf-frontmatter.schema.json`.** `architecture/containers.md` gives the Local Repository two storage forms; only the SQLite index had a schema. The bundle contract covers layout, identity, frontmatter, links, reserved filenames, attachments and invariants, with the JSON Schema (2020-12) providing a machine-checkable frontmatter model that encodes OKF's required/recommended/optional distinction and explicitly permits unknown properties.

CAP-PORT-01 is scoped to Notes the application *creates*, and a permanently non-conformant bundle is supported. What makes the copy cheap is the plaintext, not the conformance — restated, with the conformance check reporting rather than gating, since refusing to export a Workspace the user is entitled to take elsewhere would invert the capability.
- **The index-connection obligation was literally unsatisfiable.** "`PRAGMA foreign_keys = ON` before any other statement" cannot hold on a SQLCipher connection, where `PRAGMA key` and the unlock probe necessarily come first. Restated as "immediately after the key pragma, and before any statement that touches a table" — stating an obligation the file it cites cannot meet invites the reader to discount it.

- Corrected the SQLCipher encryption claim. It was documented as AES-256-GCM; SQLCipher 4.x is in fact AES-256-CBC with per-page HMAC-SHA512 authentication (Encrypt-then-MAC) and PBKDF2-HMAC-SHA512 key derivation, confirmed against `PRAGMA cipher_settings`. This is not an AEAD, and the distinction matters for EPIC-C's tamper-resistance reasoning. The same wording was corrected in the `UIDB-B002` acceptance criterion.

Provisioning a real SDK was tried and reverted: it costs a measured 14.9 GiB closure on a desktop-only tree and appends NDK, build-tools, `libglvnd` and `vulkan-loader` paths to `LD_LIBRARY_PATH`, which the environment deliberately leaves untouched.
- Adopted the devenv v1.4+ `.envrc` form (`eval "$(devenv direnvrc)"`). The older `source_url` recipe pinned a direnvrc revision and content hash by hand, which drifts from both the installed CLI and `devenv.lock`; the CLI now emits the direnvrc matching its own version.
- Recorded the FRB version triple as a risk to manage rather than a documented rule: the Nix-pinned `flutter_rust_bridge_codegen` is versioned independently of the `flutter_rust_bridge` Rust crate and Dart package. Upstream publishes no explicit version-matching requirement (manual and troubleshooting pages checked), so the guidance to keep the three aligned is flagged for empirical confirmation at CORE-A001.
