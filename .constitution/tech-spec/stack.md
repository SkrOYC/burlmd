## Managed validation bootstrap

The standard public runner labels define evidence capabilities, not a universal gate for every ticket. Linux x86-64 `ubuntu-24.04` and Apple Silicon `macos-26` can run common functional and performance evidence. Linux can also run exact headless platform-regression capture. macOS 26 can produce the sole authoritative product visual evidence. Apple Silicon `macos-15` can produce functional compatibility evidence only. Each managed run accepts only the exact ticket-specific subset in `requiredEvidenceClasses`.

GitHub documents 4 CPUs, 16 GB of memory, and 14 GB of storage for standard x86-64 Linux runners. It documents 3 M1 CPUs, 7 GB of memory, and 14 GB of storage for standard arm64 macOS runners. These allocations define the reference classes, but they don't pin a physical host. CPU scheduling, storage throughput, and host contention remain outside the project's control.

The `ubuntu-24.04`, `macos-26`, and `macos-15` labels pin the operating-system major, not an immutable image. GitHub updates hosted images weekly. Every run must therefore capture `ImageOS`, `ImageVersion`, the full OS release, architecture, CPU model and count, memory, storage, and its 1920x1080 at 60 Hz logical viewport record. `viewport.verified` is true only when a role-owned probe observes that exact viewport. A false value doesn't claim an observed viewport. Roles that provide `performance`, `linux-platform-regression`, or `macos-authoritative-visual` must record true. `CI-M003` provides none of those classes, so its macOS roles can record false and it must not add a host-display probe. Aggregation must not combine performance or visual evidence across different image versions. Repository toolchains remain pinned through Nix inputs, `rust-toolchain.toml`, `Cargo.lock`, and `pubspec.lock`.

Role output has two schemas. The `contracts/ci-role-evidence.schema.json` file validates the candidate manifest and the separate pre-completion sealing receipt. The receipt records `job.check_run_id` and immutable identity and digest facts, but it has no final job state. The `contracts/ci-evidence.schema.json` file validates the coordinator's accepted or rejected aggregate after post-completion job, artifact, and provenance enrichment. These contracts keep receipt and bundle hashes outside the bytes they describe.

Each role has a distinct reusable workflow with two static jobs: `candidate` and `seal`. The jobs run on separate fresh environments with the role's same fixed hosted label. `candidate` checks out the tested source as data and has no OIDC, attestation, or Actions authority. Candidate artifacts are untrusted. On Linux, candidate commands run with `env -i` in a Bubblewrap `0.11.2` private PID namespace and must prove that a double-fork probe does not survive teardown. On hosted macOS, cleanup is bounded and does not claim universal candidate-process containment. `seal` needs the successful candidate job, never executes candidate bytes, validates identity, job, hosted label, artifact IDs, REST digests, safe archive structure, schemas, and member hashes, and alone receives OIDC and attestation authority. During execution, `seal` records a check-run locator but doesn't predict its conclusion. After the attempt completes, aggregation requires the matching job API object to report success and match the signed hosted provenance. A trusted `workflow_dispatch` caller on `master` references each local workflow through a static `./.github/workflows/...` path, so GitHub resolves it from the caller's signer commit. ADR-019 records this platform-specific trust decision.

## Core Engine & Local Index
- **Language:** Rust (edition 2021)
- **FFI Bridge:** `flutter_rust_bridge` (v2)
- **Git Implementation:** Hybrid. `gix` (gitoxide) `0.86.0` handles `clone` (checkout included) and `commit` (tree construction via the `tree-editor` feature, object/ref writes, and rebuilding `.git/index` from the committed tree). The `git` CLI is shelled out to for `push` and `pull`: as of `gix` 0.86.0, upstream's own `crate-status.md` lists `push` as entirely unimplemented (no send-pack/receive-pack client plumbing at all), and its `merge` support covers only blobs and trees, not commits — there is no three-way commit merge, and therefore no way to produce the raw `<<<<<<<`/`=======`/`>>>>>>>` conflict markers `flow-conflict-resolution.md` depends on, purely through `gix`. `pull` shells to `git fetch` + `git merge` (equivalent to `git pull --no-rebase`) specifically because `git merge` leaves those markers in the working tree on conflict without destroying them, which is required. Verified against `gix` 0.86.0 (published 2026-07-23 on crates.io) and the `GitoxideLabs/gitoxide` `crate-status.md` at the same date; re-check this split on any future `gix` major/minor bump, since push and commit-merge are both active development areas upstream.
- **Local Database:** SQLite via `rusqlite` (with the `bundled-sqlcipher` feature). As of `rusqlite` 0.40 there is no separate `fts5` feature: FTS5 is compiled into the bundled amalgamation by default, and `bundled-sqlcipher` transitively enables `bundled`. Verified in the devenv shell against SQLCipher 4.14.0.
- **HTTP Client:** `reqwest` `0.13.4` (blocking, `rustls` TLS backend, `json`/`form` features) — a direct dependency added for SYNC-C002's GitHub OAuth PKCE token exchange and `GET /user` lookup (`api::auth`). This is not a second HTTP stack: `gix`'s `blocking-http-transport-reqwest-rust-tls` feature (see Git Implementation above) already resolves the same crate transitively, confirmed by a single `reqwest v0.13.4` entry in `Cargo.lock`; the direct dependency only adds the `blocking`/`rustls`/`json`/`form` features `api::auth` needs on top of the already-resolved version.
- **Markdown Parser:** `pulldown-cmark` `=0.12.2` (with a custom pre-processor for Git conflict markers). Two of its APIs are load-bearing for ADR-007, both verified present in the vendored source rather than assumed: `Parser::into_offset_iter()` (`src/parse.rs:1310`), which yields a byte range per event and is what makes span-preserving source splicing possible without replacing the parser; and `Options::ENABLE_YAML_STYLE_METADATA_BLOCKS` (`src/lib.rs:559`) together with `Tag::MetadataBlock`/`MetadataBlockKind`, which locate the OKF frontmatter block as a span so it can be read without ever being re-serialized. `0.13.4` is the current release (May 2026); the intent is to stay at `0.12.2`, because it demonstrably has both APIs and a minor bump carries its own parse-behavior risk, and the two-minor gap should be evaluated rather than left indefinitely.

  **The manifest expresses that pin.** `rust/Cargo.toml` declares `pulldown-cmark = "=0.12.2"` — an exact requirement, not a caret range — since `WSPC-D003`. Before that it declared `"0.12"`, which `Cargo.lock` happened to resolve to 0.12.2 but which `cargo update` would have moved, taking the ADR-007 splice path with it. The exact pin is what makes "version-pinned" true of the one dependency where a specific API is load-bearing rather than merely convenient; a bump is now a deliberate manifest edit that re-runs the two source-line verifications above.
- **YAML Reader:** `saphyr` `0.0.11` — reads and validates the OKF frontmatter block. Read-only by design: ADR-007 treats the block as a byte span that is spliced rather than round-tripped, so ADR-004's "preserve unknown keys verbatim" obligation needs no writer and no serde derivation. A full YAML 1.2 parser is still required rather than ad-hoc extraction, because OKF §11 makes *parseability* itself the conformance test, and hand-rolling a parser for a real specification is precisely the failure this project's standards forbid. `serde_yaml` and `serde_yml` are both deprecated and archived; `saphyr` is the actively maintained YAML 1.2 implementation, at the cost of being pre-1.0 (see Compatibility Policy).

  `saphyr-parser` `0.0.11` — the lower-level event parser `saphyr` itself is built on, and already resolved transitively before `WSPC-D002`'s post-merge review round added it as a direct dependency. `okf::frontmatter::read_frontmatter` cannot hand `saphyr::Yaml::load_from_str` untrusted YAML unconditionally: that loader clones the subtree an alias references at every occurrence, so a small, deliberately nested block of anchors ("billion laughs") aborts the process via an uncatchable allocation failure rather than returning non-conformant — measured at ~430 bytes across 9 nesting levels. `okf::frontmatter::contains_alias_reference` pre-scans the same raw token stream `saphyr`'s loader consumes and rejects the block on the first alias token, before anything is materialized, closing the exploit without hand-rolling a second YAML implementation. `proptest` (dev-dependency only, not shipped) backs the mandatory round-trip property test on the link-serialization path (`okf::links::tests::link_round_trips_through_serialize_and_a_real_parse`), per this ticket's own Gherkin requiring "a property test over a generator/corpus, not single-word fixtures" — the same pattern `ctor` already follows for `security::keyring`'s tests below.
- **Hashing:** `sha2` `0.10.9` — already a direct dependency for SYNC-C002's PKCE S256 challenge, reused for the `base_revision` content hash defined in ADR-007 decision 7. No new dependency.

## Security & Cryptography
- **Secure Storage (Rust):** `keyring` - handles direct retrieval of OAuth tokens and AES keys from the OS hardware enclave without passing them through Dart memory. **Known issue (`keyring` 4.1.5):** the crate's lazy default-store initialization (`v1::Entry::new`'s `SET_CREDENTIAL_STORE` compare-exchange) has a narrow startup race under concurrent first use — two threads calling `Entry::new` for the very first time in the process at nearly the same instant can leave the loser observing `NoDefaultStore` even though the winner is already mid-flight and registers the store milliseconds later. Production code (`api::auth::new_keyring_entry`) rides this out with a short bounded retry; the test suite additionally warms the store up front via a `ctor`-based initializer (`ctor` is a dev-dependency only, not shipped). Re-verify this behavior if `keyring` is upgraded.
- **Database Encryption:** `sqlcipher` (bundled with `rusqlite`) - provides transparent AES-256-CBC encryption of the SQLite index file on disk, with each page authenticated by HMAC-SHA512 (Encrypt-then-MAC). This is not an AEAD construction; threat-model reasoning about tamper resistance must not assume GCM semantics. Per the SQLCipher design document (<https://www.zetetic.net/sqlcipher/design/>): "The encryption algorithm is 256-bit AES in CBC mode", and "every page write includes a Message Authentication Code (HMAC-SHA512) of the ciphertext and the initialization vector at the end of the page". Cross-checked locally by reading `PRAGMA cipher_settings`; the instrument there was the standalone 4.16.0 CLI, while the shipped version is the 4.14.0 vendored by `bundled-sqlcipher`.
- **Key application:** the root key from `keyring` (see below) is already a full-entropy 256-bit CSPRNG value, so it is applied to SQLCipher via the raw-key PRAGMA form — `PRAGMA key = "x'<64 hex chars>'"` — which sets the 32 key bytes directly with **no KDF applied**. SQLCipher's passphrase-mode PBKDF2-HMAC-SHA512 (256,000 iterations) exists to strengthen low-entropy human passphrases; running it on already-random key material adds cost with no security benefit, so this project deliberately does not use passphrase mode. (Corrected in v1.0.2 — the encryption bullet previously stated the key was "derived via PBKDF2-HMAC-SHA512", which described passphrase mode rather than this project's actual raw-key mechanism.)

## Compatibility & Upgrade Policy
- **Developer Environment:** The entire toolchain is provisioned by `devenv` (Nix). `devenv.lock` pins `nixpkgs`, `rust-overlay` and `git-hooks`, so the toolchain closure resolves identically across machines and CI. Note the boundary stops there: `pub` and `cargo` still resolve package registries outside the store, pinned by `pubspec.lock`/`Cargo.lock` once those exist, and the `devenv` CLI that reads the lock is itself installed outside it.
- **Android SDK:** Not provisioned, and discovery is pinned shut. `ANDROID_HOME` and `ANDROID_SDK_ROOT` point at an in-repo path that deliberately holds no SDK, because Flutter otherwise scans well-known home-directory locations and silently adopts whatever SDK a contributor happens to have installed — the one part of the toolchain `devenv.lock` could not govern. `flutter doctor` now reports `ANDROID_HOME = <repo>/.sentinels/no-android-sdk but Android SDK not found at this location.` — the same result on every machine, instead of a per-host one. Note this is deliberately *not* Flutter's "Unable to locate Android SDK" message, which is the branch taken when no `ANDROID_HOME` is set at all: that was the pre-fix state. A real pinned SDK belongs here when mobile is unshelved, at versions current at that time; provisioning one now would cost a 14.9 GiB closure on every desktop-only checkout (measured) and would append NDK, build-tools, `libglvnd` and `vulkan-loader` paths to `LD_LIBRARY_PATH`, which the environment deliberately leaves untouched.
- **Web Target:** Also out of scope, and pinned shut by the same mechanism: `CHROME_EXECUTABLE` points at an in-repo path holding no browser. Left unset, Flutter resolves one off the host `PATH` and reports a green `[✓] Chrome` that `devenv.lock` does not govern — the same ambient per-machine state the Android sentinel closes.
- **devenv Modules Input:** `devenv.lock` pins the `devenv` module set to a `master` revision with no `ref`, so `devenv update` moves it to whatever `master` is that day, independently of the CLI it was verified against (2.1.2). Pinning `inputs.devenv.url` to the CLI's release tag would close that drift; deferred, but re-verify the shell after any `devenv update`.
- **Rust Toolchain:** Pinned via `rust-toolchain.toml` (currently `1.97.1`), consumed by devenv through `languages.rust.toolchainFile` and by rustup users directly. `1.95` is a hard floor because `libsqlite3-sys >= 0.38` requires `cfg_select!`, which was stabilised in Rust 1.95.0 (rust-lang/rust#149783).
- **Flutter SDK:** Pinned via `nixpkgs` (`flutterPackages.v3_44`, currently 3.44.3 / Dart 3.12.2) rather than `fvm`. `fvm` downloads unpatched upstream SDK binaries that do not execute on NixOS and would bypass the Nix store, defeating reproducibility.
- **Flutter localization generation:** Flutter 3.44.3's `flutter gen-l10n --help` marks `--synthetic-package` deprecated and unavailable; its default output is the ARB directory, not `.dart_tool`. The repository therefore pins `l10n.yaml` to `arb-dir: lib/l10n`, `output-dir: lib/l10n/generated`, and `output-localization-file: app_localizations.dart`. `EDIT-F006` adds the SDK `flutter_localizations` package and direct `intl` `0.20.2` (the version the pinned Flutter 3.44.3 `flutter_localizations` package requires) with `flutter pub add "flutter_localizations@{sdk: flutter}" intl@0.20.2`, committing `pubspec.lock`. Generated Dart under `lib/l10n/generated/` is repository-owned and committed so pre-commit and deterministic builds do not depend on a hidden synthetic package.
- **Flutter text-input API verification:** ADR-012's direct `TextInputClient` proxy is verified against the pinned **Flutter 3.44.3 / Dart 3.12.2** SDK source, not an ambient Flutter installation. `packages/flutter/lib/src/services/text_input.dart` requires `currentTextEditingValue`, `currentAutofillScope`, `updateEditingValue`, `performAction`, `performPrivateCommand`, `updateFloatingCursor`, `showAutocorrectionPromptRect`, and `connectionClosed`, and declares `TextInput.attach(TextInputClient, TextInputConfiguration)` plus `TextInputConnection.show`, `setEditingState`, and `close`. `packages/flutter/lib/src/widgets/actions.dart` supplies `Actions`/`CallbackAction`; its paired `DefaultTextEditingShortcuts` source binds the desktop delete and clipboard intents ADR-012 overrides explicitly. The SDK path resolves from the pinned Nix package during the development shell. Re-verify this exact surface on any Flutter patch/minor bump before changing the proxy.
- **FRB Version Triple:** The installed `flutter_rust_bridge_codegen`, Rust crate, and Dart package are all `2.12.0`. The merged base doesn't contain `scripts/check-generated-bindings.sh`. `CI-M003` must implement the non-mutating checker specified in `guidelines.md` before invoking it as a bootstrap gate. The checker snapshots both generated surfaces, runs the provisional generator, detects byte drift, and restores the exact precheck state before exit. This authorization is provisional: final Stage 3 must revalidate the generator, both runtimes, configuration, and generated outputs after every evidence-driven dependency decision. A later ticket can't cite the bootstrap pin as final approval.
- **Managed coordinator isolation:** `CI-M003` adds Linux-only `pkgs.bubblewrap` to `devenv.nix`. The `devenv.lock` Nixpkgs revision `6004ea8c229fe9d41b21c6f4c76bf6c2e10771dd` resolves Bubblewrap `0.11.2`. The trusted launcher enumerates, closes, and verifies every nonallowlisted descriptor before it starts Bubblewrap. Bubblewrap supplies user, mount, process, network, and filesystem isolation only. Managed-Spike aggregation runs only in the Linux coordinator role and requires successful descriptor, namespace, mount, and network probes. The coordinator receives a minimal read-only Nix runtime closure, verified read-only inputs, and one writable output mount. It doesn't receive the repository, host home, credential configuration, or network. If the hosted kernel or policy blocks this isolation, aggregation is rejected; credential clearing alone isn't a fallback.
- **OKF Specification Version:** Pinned to v0.2 by ADR-004. The specification's §12 states that a minor bump adds backward-compatible optional fields while a major bump may rename required fields or change reserved filenames — but do not plan against that stated policy, because upstream has already departed from it. The only minor bump the format has had, v0.1 to v0.2, carried two breaking changes in its own §13.1: `timestamp` superseded by `generated.at`, and the body `# Citations` list superseded by the `sources` frontmatter field. **Treat every OKF revision, minor or major, as potentially breaking** and as an explicit decision to re-evaluate against `data-models/okf-bundle.md`; never as an automatic adoption. The format is young (v0.1 shipped June 2026, v0.2 within weeks), so movement is likely and this is not a theoretical concern. Note also that we ship untagged: §12 permits declaring `okf_version` only in a bundle-root `index.md`, which ADR-004 decision 6 declines to generate.
- **`saphyr` Pre-1.0 Risk:** The pin is `0.0.11` (published 2026-07-11). The crate is at `0.0.x`, has shipped multiple releases in a single day, and changed publishing maintainer partway through its history — so its API should be assumed unstable across any bump. This is tolerable here specifically because the surface consumed is tiny and read-only (parse a block; extract two scalar strings), which caps the blast radius of a breaking change at a single module. It would not be tolerable if the frontmatter block were being serialized back out. Re-verify on every bump. `saphyr-parser` is pinned to the identical `0.0.11` for the same reason and carries the same risk profile — it is published from the same repository in lockstep with `saphyr`, so the two are re-verified together.
- **Data Schemas:** Handled through `rusqlite` `PRAGMA user_version`. Fresh
  creation, recoverable version-zero crash states, and version publication are
  one immediate SQLite transaction. Version zero is not assumed empty: a full
  v1 `notes` shape is migrated before v2 is published, while a v2 shape or the
  deterministic `workspaces`-only prefix is completed as v2. Opening a version
  1 index adds and backfills `notes.title_lookup_key`, then creates its lookup
  index in that same transaction. The derived key uses NFKC, full Unicode case
  folding, and NFC, so title-prefix lookup does not depend on SQLite's
  ASCII-only `LIKE` and `NOCASE` behavior. An index with a later version
  remains unchanged.
- **Key Rotation:** The root AES key is randomly generated on first boot and never leaves the device's secure enclave. Key rotation is currently out of scope unless device compromise is suspected.
